# Dev Weekly Journal

從 git log 整理一週的開發紀錄，產生可直接貼到 Medium 的開發週記草稿。

## 適用情境

- 使用者說「幫我寫這週的週記」、「整理週記」、「這週的開發週記」
- 使用者提供日期區間，要求根據 git log 整理成週記

## 不適用情境

- 這週沒有 commit，或目前目錄不是 git 專案
- 使用者只是要 commit message 的逐字翻譯，不是整理過的敘述
- 使用者已經寫好內容，只是要單純轉換格式（直接照使用者提供的內容排版即可，不用重新分析 git log）

## 已登記專案

目前只整理以下專案的週記，不用每次詢問 repo 路徑：

- **PicShare (image-sharing-platform)**：`d:/project/claude_code/image-sharing/image-sharing-platform`

之後若使用者要整理其他專案的週記，先詢問該專案的 git repo 路徑與暱稱，並在這裡新增一列。

## 工作流程

1. 確認範圍（一次最多問 2 題，若使用者已提供則不重複問）：
   - 要整理哪個專案 — 優先比對上方「已登記專案」清單；若使用者提到的專案不在清單中，詢問 git repo 路徑並提醒之後會登記進清單
   - 日期區間（預設上週日～今天週六；使用者可自訂）
   - 週數一律留空，不詢問、不推算（見下方輸出格式）
2. 執行 `git -C "<repo 路徑>" log --since="<開始日期>" --until="<結束日期>" --oneline --all` （或依實際分支調整）讀取範圍內的 commit
3. 依 commit 發生的日期分群（哪幾天有變動），歸納成 2–4 個主題區塊。**不要逐條照抄 commit message**，要整理成使用者看得懂的功能敘述，適度保留技術細節（API 路徑、檔案名稱、套件名稱）
4. 若某天的除錯或重構過程特別扎實、值得記錄，整理成「本週小結」的心得段落，**控制在五句以內**，不需列出每一個踩過的坑，只總結學到什麼
5. 依下方輸出格式產出純文字草稿，結尾附上專案的 GitHub 連結（若使用者有提供）
6. 在草稿下方用分隔線 `---` 隔開，附上這則只給使用者自己看、不用貼到 Medium 的資訊：
   - `對應專案：<專案暱稱>（<repo 路徑或名稱>）`
   - 貼到 Medium 前要手動處理的提醒，逐行列出（不要壓縮成一段文字或用 ①②③ 串在一起）：
     - 補上週數：標題裡的「(W)」是刻意留空的，需要自己填入正確的週數（Wxx）
     - 修改編號清單：貼上後「1. 2. 3.」會全部變成「1. 1. 1.」，需要手動把每一項的數字改回正確順序
     - 手動放入圖片：功能截圖／示意圖（例如這週改版的畫面）、文末的專案 banner 圖，草稿只有文字，圖片要自己插入

## 輸出格式

```
[開發週記] <專案暱稱> | <專案名> (W) — <本週重點1>、<本週重點2>、<本週重點3>

<1–2 句話總結這週做了什麼，不逐條列>

💻 本週開發進度

1. <主題一標題>

- <子項目：說明。>
- <子項目：說明。>

2. <主題二標題>

- <子項目：說明。>

3. <主題三標題（若有）>

- <子項目：說明。>

📈 本週小結

<五句以內的心得段落>

<GitHub repo 連結（若有）>
```

子項目一律用 `- ` 開頭（對應 Medium 貼上後的項目符號清單），不要省略。標題的週數固定留空為 `(W)`，不要自己填數字。以上區塊是要直接複製貼到 Medium 的內容，不要混入其他文字。

## 安全限制

- 不自動發布到 Medium，只產生文字草稿供使用者複製貼上
- 不讀取或輸出 .env、金鑰、token 等敏感檔案內容
- commit message 若含內部網址、密碼字串等敏感資訊，整理時不照抄進週記
